# DAILY KILL SCAN
Run after the constraint is named, before the contract is written. Target 10 minutes.
"Nothing new today" is a valid and expected answer on most days.

## PURPOSE — hold this tone throughout
Every artifact this program builds exists to accurately determine **what will prevent us from
making money.** Not to describe the market. Not to be rigorous for its own sake. This scan
asks one question in eight ways: what is quietly making a measured edge unreachable, that
nobody is currently tracking?

## EVIDENCE RULE
Every item must name the artifact on disk that would show it — a file, a hash, a count, a git
state, a frozen line. An item you cannot ground is labelled SPECULATION or dropped. Unknown is
a valid answer. Do not fill the form.

DO NOT reassure. DO NOT list what is already being managed. DO NOT invent items to reach a
count.

---

## PASS 1 — THE INSTRUMENT'S LIMIT
Do this first. It is the program's documented failure mode.

Seven times in this program a limit of a measuring instrument was recorded as a caveat when it
was actually a constraint on what the measurement could conclude. Entry rank for entry time.
Supply consumption for entry timing. Liquidity for price. Detection latency for actionable
latency. Address-distinctness for actor-independence.

Ask, against today's work: **is anything we are measuring a PROXY for the thing we actually
need?** If yes — does the proxy's limit make a rule 5 clause UNSATISFIABLE, or merely
imprecise? Say which. A caveat that makes a clause unsatisfiable is a STOP, not a footnote.

## PASS 2 — WHICH CLAUSE FAILS FIRST
Rule 5 has five clauses. Walk them against today's state and name the one closest to failing,
with the artifact that shows it:
- **(a)** could a stranger execute the rule from the artifact alone
- **(b)** 30 independent observations, independence ESTABLISHED not assumed
- **(c)** beat a declared null by a margin declared BEFORE the test
- **(d)** byte-identical replay from pinned snapshots
- **(e)** names what it lets me do with money

If any clause is unsatisfiable on the CURRENT DESIGN — not merely unmet — that is the finding
and it outranks everything else in the scan.

## PASS 3 — SINGLE POINTS OF FAILURE
What is this program depending on that nobody thinks of as a dependency because it has always
worked? The websocket with no HTTP fallback. One laptop. One disk. One base model reasoning as
both finder and referee. Free-tier access. An unpushed commit.

For each: what happens the day it stops, and is there a backup? Name the ones with none.

## PASS 4 — CASCADES
What single event breaks two things at once? Precedent in this program: the machine dying
mid-fetch didn't only lose a capture — it lost an ordering proof that existed on one disk. Look
for one event taking out supports that appear independent.

## PASS 5 — SILENT CLOCKS
What has a date nobody is tracking? 2026-09-28 collection close · ~~2026-09-30 stopping rule~~
(**STRUCK 2026-08-25 — no calendar stopping condition**) ·
the $2,000 cash floor · disk free space against the 2 GB guard · any override-clause abandon-by
date · a free-tier credit balance · an unpushed commit's exposure window.

Report each with its current measured value and days remaining. **A clock with no measured
value is the finding.**

## PASS 6 — THE WHISPER
What happened ONCE and got explained away in the last few days? A single event usually means
nothing — but a single event that was EXPLAINED AWAY deserves a second look. Report what was
dismissed and what would confirm or kill it.

## PASS 7 — THE UNPRICED FAILURE BRANCH
Where are we assuming the good outcome? Specifically: **what happens if today's contract
returns the NULL?** Is that outcome pre-declared as publishable, or does it leave the program
with no next step? A contract whose failure branch is unplanned is a contract that will produce
a rescue when it fails.

## PASS 8 — WHAT HAS BEEN TRUE SO LONG WE STOPPED SEEING IT
What structural fact of this program is invisible because it is constant? Zero revenue.
Seventeen contracts, no dollar. One venue, one chain. Both threads sharing a base model. Is any
of it more load-bearing than it looks?

## OUTPUT
As many items as are real, and no more. **Zero to four is normal.**

For each:
```
THE BLIND SPOT     — one sentence, and what it prevents us from making money on
THE EVIDENCE       — the file, hash, count, or git state that shows it
THE TRIPWIRE       — the earliest observable signal, and whether it is already visible
THE CHEAPEST ACTION— what would de-risk it today
MONITOR or ACT
SPECULATION        — flag it if the item is reasoned rather than read
```

Then: **THE ONE I'D BET ON** — the single item most likely to actually bite, with why.

If the scan finds nothing new, say **"nothing new today"** and name what you checked. That is a
better answer than a manufactured list, and it is the expected answer most days.
